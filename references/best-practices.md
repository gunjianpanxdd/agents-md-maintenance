# Best Practices: what high-performing instruction files share

Distilled from the agents.md standard (60,000+ repos), GitHub's analysis of 2,500+ agent definition files, and cross-repo statistics from high-star projects (n8n, apache/airflow, temporalio, LangFlow). Use this as the acceptance checklist for every proposed rule.

## Consensus core sections

A healthy standing instruction file covers these, roughly in this order:

1. **Commands first.** The highest-leverage lines in the file: exact install/dev/test/lint/build commands, with flags, in code blocks (a bullet-list command can be read as prose). Include environment variants (docker vs local, CI vs dev) when both exist. Agents that can self-verify produce dramatically fewer broken changes.
2. **Boundaries** — three tiers, explicit:
   - 🚫 **Never**: generated dirs, vendored code, secrets, lockfile deletion, brand assets
   - ⚠️ **Ask first**: dependency changes, schema changes, public-facing edits
   - ✅ **Always**: run X before commit, put temp files in Y
3. **Project layout** — the 30-second directory tour, so the agent doesn't discover it by `ls`-ing.
4. **Conventions that diverge from defaults.** Agents carry strong priors from training data; anything where this repo deviates from the framework default must be stated, or it will be done "the normal way".
5. **Git/PR workflow**: commit message format, what must pass before commit.

## Rule-quality checklist

- [ ] **Specific over aspirational.** "React 18 + TS + Vite" not "modern web app". "Use async/await, not .then()" not "clean async code".
- [ ] **Imperative, executable, verifiable.** Every rule either names a command that checks it or describes an observable outcome.
- [ ] **Boundaries carry reasons.** "Never edit `src/generated/` — regenerated by protobuf, run `make generate`" survives edge-case contact; a bare prohibition doesn't.
- [ ] **Prohibitions carry replacement paths.** "Don't X" alone produces deletion, not correction. Real failure modes are rewrites, not removals.
- [ ] **Criteria + real ✗/✓ pairs, not banned-word lists.** Word lists get paraphrased around; a criterion plus one or two concrete examples does not. (Budget the examples: the model imitates their shape and length.)
- [ ] **Hard requirements carry fallbacks.** "Each section must contain X — when material is insufficient, do Y instead", or the rule forces fabrication.
- [ ] **One rule, one job.** Writing and reviewing are separate rules; extraction and validation are separate rules.
- [ ] **Effective-condition visible.** A conditional rule states its trigger ("only when editing prompt templates"), so an agent knows when it applies and when it doesn't.

## File-level hygiene

- **Length**: standing context ≤ ~150–200 lines. Longer files dilute adherence to every rule in them (and cost prompt-cache freshness on every request). If over: move per-domain detail to nested files or `docs/` with trigger conditions.
- **Freshness**: a 40-line file that is true beats a 400-line file that is half-stale. Update the instruction file in the same change that makes a convention change; CI can enforce (`test $(wc -l < AGENTS.md) -le 200`).
- **No README duplication**: instruction files are operational runbooks, not marketing. Keep project vision out.
- **No generic section titles** ("Coding Standards" invites generic advice; "TypeScript rules in this repo" invites repo-specific ones).
- **Safety is first-class**: a dedicated security section that wins on conflict; never store real secrets or vault paths in the file.
- **It is not the only quality gate**: instruction files shape agent behavior; they cannot verify visual rendering or product judgment. Pair with review layers.

## Anti-patterns (found repeatedly in the wild)

| Anti-pattern | Why it fails |
|---|---|
| Copy-pasting README into the file | No operational value; doubles staleness surface |
| "Follow existing patterns" without saying where they live | Agent can't act on it; it guesses |
| Vague stack description | Agent fills gaps with framework defaults |
| Commands that need human context ("deploy to staging") without stating whether the agent may run them | Agent either blocks or does something irreversible |
| Five parallel "highest priority" rules | Priorities collapse; the model implicitly ranks by length |
| Rules that only exist in chat history / memory, never in the file | Lost at the next session boundary — the most common silent failure |
